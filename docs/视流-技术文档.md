# 用 Kotlin 把旧手机变成 RTSP 摄像头：Camera2 + MediaCodec + OpenGL 全链路拆解

> 一个不到 4000 行 Kotlin 的原生 Android 推流应用，没有 FFmpeg、没有第三方流媒体 SDK，从相机采集到 RTP 打包全部自己实现。
> 支持 RTSP 拉流、RTP/UDP 广播、息屏后台保活，并能在 1080P30 下稳定输出约 4 Mbps 的 H.264 码流。

---

## 一、这个应用能做什么

「视流」是一个单 Activity 的 Android 应用，核心目标只有一句话：**把手机摄像头变成局域网内任何播放器都能拉取的视频源**。

功能清单：

- 后置 / 前置 / 外接镜头自动识别，单镜头设备自动隐藏切换入口
- 分辨率与帧率完全来自设备实际能力，不写死任何档位
- RTSP 服务（端口 8554），支持 TCP interleaved 与 UDP 两种传输
- RTP over UDP 广播（端口 9998），无需握手，探测即入会
- 可选 Basic 鉴权（`admin:密码`）
- 推流中实时显示帧率、实际码率、客户端数量与丢包数
- 前台服务保活：息屏、切后台、锁屏都不中断
- 横竖屏切换、前后镜头切换均为百毫秒级，不重建相机会话

实测数据（华为 MRD-AL00，Android 9 / API 28，1080P30 档位）：

| 指标 | 实测值 |
| --- | --- |
| 编码输出帧率 | 约 26–27 fps（室内弱光，相机自动降帧） |
| 实际码率 | 3.8–4.4 Mbps（CBR 目标 4.35 Mbps） |
| RTSP 并发客户端 | 2 路 TCP 同时拉流正常 |
| RTP 广播拉流 | 单帧解码正常 |
| 息屏后台 | 20 秒后仍可正常拉流 |

需要说明的是：**当前版本只推视频，不采集音频**；UDP 广播没有鉴权，仅建议在可信局域网内使用。

## 二、整体架构：一条相机链路，两个出口

绝大多数 Android 推流方案会把「预览」和「编码」拆成两条独立链路：相机同时输出两个 Surface，一个给 TextureView，一个给 MediaCodec。这样做实现简单，但方向、比例、镜像要维护两套逻辑，横竖屏切换时极易出现预览和码流不一致。

本项目反其道而行：**相机只输出一个 Surface，所有画面处理集中在一套 OpenGL 管线里，再由它同时分发到预览和编码器。**

```
Camera2 ──► SurfaceTexture ──► GL 管线（旋转 / 镜像 / 裁剪）
                                   │
                                   ├──► 预览 EGLSurface（TextureView）
                                   └──► 编码 EGLSurface（MediaCodec InputSurface）
                                                │
                                          H.264 Annex-B
                                                │
                        ┌───────────────────────┴───────────────────────┐
                        │                                               │
                 RTSP Server :8554                              RTP Broadcaster :9998
             （TCP interleaved / UDP）                        （无握手 UDP 广播）
                        │                                               │
                  每客户端 RTP 打包                                统一 RTP 打包
                  每客户端发送队列                                客户端列表 + 超时清理
```

模块划分（共 15 个 Kotlin 文件、约 3940 行）：

- `StreamController`：应用层状态机，编排镜头、分辨率、编码器、服务与统计
- `CameraCatalog` / `CameraSession`：相机能力探测与 Camera2 会话
- `RotatingGlPipeline`：EGL + SurfaceTexture + 顶点纹理坐标旋转
- `H264Encoder`：MediaCodec 编码与 Annex-B 输出
- `RtspServer` / `H264RtpPacketizer` / `RtpBroadcaster`：流媒体协议栈
- `StreamService`：前台服务与 WakeLock
- `StreamScreen`：Compose UI

## 三、技术关键点 1：预览与码流必须「同源渲染」

这是整个项目最核心的设计，也是踩坑最多的地方。

### 3.1 为什么不用两条链路

早期版本用 TextureView 自己的矩阵做预览，编码走另一套 OpenGL。结果是：

- 竖屏时预览是横的，码流却是正的（或反过来）
- 预览按控件铺满，码流按相机比例输出，构图不一致
- 横竖屏切换要同时改两套参数，调一次要验证两个画面

最终方案是：**相机画面只进一条 GL 管线，预览和编码用同一份纹理坐标渲染两次**，只是视口不同。

### 3.2 管线内部结构

- `SurfaceTexture` 以 `GL_TEXTURE_EXTERNAL_OES` 挂到 GL 线程
- 每帧 `updateTexImage()` 后，分别向两个 EGLSurface 各画一次
- 编码输出：`glViewport(0, 0, 编码宽, 编码高)`，整帧铺满
- 预览输出：按画面宽高比等比放大后居中裁剪，铺满控件
- 两路共用同一个顶点缓冲，旋转和镜像只发生在纹理坐标上

这样做的直接收益是：**方向、比例、镜像永远只改一处**。

### 3.3 旋转不是旋转顶点，而是旋转纹理坐标

顶点始终铺满视口，只改变四个角的 `(s, t)` 采样坐标：

```kotlin
when (rotationDegrees) {
    90  -> { s = 1f - dy; t = dx }
    180 -> { s = 1f - dx; t = 1f - dy }
    270 -> { s = dy;     t = 1f - dx }
    else-> { s = dx;     t = dy }
}
```

这样做的好处是旋转不会产生额外的顶点变换矩阵，也不会因为视口宽高互换而出现拉伸，同时方便把镜像叠加进去：**先镜像 x，再按角度旋转**。顺序反了，前置画面会差 180°，这是实际踩过的坑。

### 3.4 时间戳必须透传

编码器对帧时间戳敏感。管线把 `SurfaceTexture.timestamp` 通过 `eglPresentationTimeANDROID` 写给编码 EGLSurface，保证 PTS 来自相机真实采集时刻，而不是 GL 送帧时刻。这样编码输出的 PTS 才是连续的，RTP 时间戳换算成 90kHz 后也不会抖动。

### 3.5 线程模型

整条 GL 管线只活在一个 `HandlerThread("shiliu-gl")` 上。切换输出 Surface、切换预览 Surface 都通过 `runOnGl {}` 同步投递并等待，避免「EGLSurface 正在销毁，帧还在往上画」的并发崩溃。

## 四、技术关键点 2：方向与镜像的完整推导

### 4.1 相机方向的官方公式

Camera2 的 `SENSOR_ORIENTATION` 描述的是「相机传感器相对设备自然方向的旋转角」。考虑屏幕旋转后，画面需要顺时针补偿的角度为：

- 后置：`sensorOrientation - displayRotation`
- 前置：`sensorOrientation + displayRotation`

代码里统一归一化到 `0/90/180/270`。这个角度决定编码宽高是否需要互换（90°/270° 时互换），而真正的像素旋转仍由 GL 纹理坐标完成。

### 4.2 屏幕旋转为什么取反

横竖屏切换时，手机和相机是一起转的。为了让世界坐标中的画面保持正向，管线需要做反向补偿：

```kotlin
activePipeline.setRotation((360 - normalizedDisplayRotation) % 360)
```

角度变化只触发一次顶点缓冲重建，不重启相机、不重建 EGL，因此横竖屏切换几乎瞬时完成。

### 4.3 前置镜像不能「立刻生效」

切换前后镜头时，`CameraSession.setLens()` 是异步的。如果先改镜像参数，旧镜头队列里尚未渲染的帧就会用新参数画出来，出现**一帧镜像画面闪帧**。

解决方案是把 `pipeline.configure(mirror, dimensions)` 延迟到新相机 `startRepeatingRequest` 真正发出之后再执行。镜像参数永远只作用于新镜头的第一帧。

## 五、技术关键点 3：让设备自己决定能推什么

`CameraCatalog` 不维护任何硬编码分辨率表，而是把三方能力求交集：

1. 相机输出尺寸：`SCALER_STREAM_CONFIGURATION_MAP.getOutputSizes(...)`
2. `SurfaceTexture` 通道支持的尺寸（因为相机实际写入的是纹理）
3. H.264 硬件编码器 `VideoCapabilities.isSizeSupported(w, h)`

再计算帧率：

```text
理论帧率 = min(AE 最大帧率, 1e9 / getOutputMinFrameDuration(size))
最终帧率 = 30 / 24 / 15 中最接近的档位
```

镜头命名也不是写死的：用焦距与传感器物理尺寸算出对角线视场角（FOV），
`≥95°` 记为超广角、`≥55°` 记为广角、其余为长焦；前置统一叫「自拍」；外接镜头单独归类。同名镜头自动追加序号。**单镜头设备只有一个选项，UI 直接隐藏切换按钮。**

这套逻辑带来的实际价值是：同一个 APK 装到不同机型上，分辨率列表永远只显示真正能跑通的组合，不会出现「选了 4K 结果编码器不支持、黑屏 6 秒超时」的情况。

## 六、技术关键点 4：低延迟编码参数

`H264Encoder` 除常规的 `KEY_BIT_RATE / KEY_FRAME_RATE / KEY_I_FRAME_INTERVAL` 外，还按 API 等级追加了直播向参数：

```kotlin
// 恒定码率，避免瞬时大帧冲高带宽
format.setInteger(KEY_BITRATE_MODE, BITRATE_MODE_CBR)

// API 29+：禁用 B 帧，消除重排延迟；关键帧前附带 SPS/PPS
format.setInteger(KEY_MAX_B_FRAMES, 0)
format.setInteger(KEY_PREPEND_HEADER_TO_SYNC_FRAMES, 1)

// API 30+：编码器实时优先、零额外缓冲
format.setInteger(KEY_LATENCY, 0)
format.setInteger(KEY_PRIORITY, 0)
```

所有可选参数都包在 `runCatching` 里，并且带 API 门槛——不同厂商编码器支持度差异极大，强行设置可能导致 `configure()` 直接抛异常。

码率不做固定值，而是按像素吞吐估算：

```text
bitrate = clamp(width × height × fps × 0.07, 0.8 Mbps, 12 Mbps)
```

以 1080P30 为例，目标码率约 4.35 Mbps；720P30 约 1.94 Mbps；VGA 触底到 0.8 Mbps。0.07 这个系数是实测折中：再低画面细节糊，再高弱网和手机发热都会明显。

关键帧间隔固定 1 秒。它同时服务于两件事：**新客户端加入后最多等 1 秒就能拿到 IDR**；丢包后的花屏也能在 1 秒内自愈。

## 七、技术关键点 5：自己实现一个 RTSP 服务端

没有引入任何流媒体库，`RtspServer` 用 `ServerSocket` + 每客户端读线程实现了 RTSP/1.0 的必要子集：

- `OPTIONS / DESCRIBE / SETUP / PLAY / PAUSE / TEARDOWN / GET_PARAMETER / SET_PARAMETER`
- SDP 由编码器产出的 SPS/PPS 动态生成，包含 `profile-level-id`、`sprop-parameter-sets`、`framerate`
- 传输层支持 `RTP/AVP/TCP;interleaved=0-1` 与 `RTP/AVP;unicast;client_port=...`
- 可选 Basic 鉴权，未通过时返回 401
- `PLAY` 响应携带 `RTP-Info: seq / rtptime`，让客户端从正确的序列号开始

DESCRIBE 时如果还没收到 SPS/PPS，会返回 `503 Retry-After: 1`，让客户端自行重试，而不是返回一个无法解码的 SDP。

### RTP 打包：单包与 FU-A

`H264RtpPacketizer` 只做两件事，但细节很多：

- 小 NAL（≤1388 字节载荷）直接单包发送
- 大 NAL 走 FU-A 分片：12 字节 RTP 头 + 2 字节 FU 头，每片总长控制在 1400 字节以内
- `PT = 96`，时钟 90000 Hz，`PTS(μs) × 90 / 1000`
- 每个访问单元最后一个 RTP 包置 marker 位

FU-A 的头构造：

```kotlin
packet[12] = ((nal[0] and 0xE0) or 28)          // FU indicator：保留 NRI，类型改 28
packet[13] = (S or E or (nal[0] and 0x1F))      // FU header：起始/结束 + 原 NAL 类型
System.arraycopy(nal, 1 + offset, packet, 14, size)  // 跳过原始 NAL 头
```

**首片绝不能携带原始 NAL 头**，否则播放器会把 FU indicator 当成普通 NAL 解析，表现为整帧花屏。这是最隐蔽的一个坑。

### SPS/PPS 补发策略

- 关键帧本身不带参数集时，打包前自动插入缓存的 SPS/PPS
- 新客户端加入时，不等关键帧，下一帧就补发一次参数集
- 每个客户端持有独立打包器，各自维护 sequence / ssrc / timestamp，互不干扰

## 八、技术关键点 6：无握手的 RTP/UDP 广播

RTSP 需要信令，对「只想快速看画面」的第三方播放器来说还是麻烦。因此额外实现了 9998 端口的 UDP 广播：

1. 客户端先向手机 9998 端口发送任意一个 UDP 包（内容无所谓）
2. App 记录该 `IP:Port`，之后把所有 RTP 包单播复制给它
3. 新客户端入会时标记 `newClientSinceLastFrame`，下一帧自动补发 SPS/PPS
4. 超过 15 秒没有发送任何 UDP 包的客户端会被清理

它不是真正的组播，而是「探测注册 + 多份单播」。好处是任何局域网设备都能用，坏处是接收端必须自己保活。用 ffplay/ffmpeg 这类只收不发的播放器时，15 秒后会被判定离线而断流——这是当前版本的已知限制。

## 九、技术关键点 7：前台服务保活

Android 的后台限制决定了：不做前台服务，息屏或切后台几分钟内推流必断。

实现要点：

- `StreamService` 以 `android:foregroundServiceType="camera"` 运行，Android 14 需要配套声明 `FOREGROUND_SERVICE_CAMERA`
- `onCreate` 中申请 `PARTIAL_WAKE_LOCK`，保证屏幕熄灭后 CPU 不被挂起
- 常驻通知展示推流地址，点击回到应用；Android 13+ 会额外申请通知权限，未授权也能推流，只是通知不可见
- `StreamController` 改为**进程级单例**（只持有 `applicationContext`），Activity 与 Service 共用同一份相机、编码器状态

最关键的是 Activity 销毁时的处理：

```kotlin
fun onActivityDestroyed() {
    if (streaming) {
        onPreviewSurface(null, 0, 0)  // 只解绑预览，编码继续
    } else {
        release()                     // 未推流则释放相机
    }
}
```

推流过程中 Activity 被系统回收（或用户按 Home），GL 管线仍继续向编码器 Surface 送帧，相机与网络线程不受影响；下次打开应用，TextureView 重新挂上预览 Surface，画面立即恢复，推流计时不中断。

## 十、技术关键点 8：每客户端独立异步发送队列

最初的 RTSP 客户端是在编码线程里直接 `socket.write + flush`。这在局域网里没问题，但只要有一个客户端网络变差或读取缓慢，`write` 就会阻塞，**编码线程被拖死，所有客户端一起卡顿**。

改造后的结构：

- 每客户端一个 `ReentrantLock + Condition + ArrayDeque`
- 编码线程只负责打包和入队，立即返回
- 独立 `rtsp-send` 线程负责真正写 socket
- 队列上限：1.5 MB 或 512 个 RTP 包

溢出策略必须按「帧」处理，不能按「包」丢弃，否则会破坏整帧：

```text
队列将溢出时：
  当前帧是关键帧 → 清空积压，整帧入队（保证 IDR 完整）
  当前帧非关键帧 → 整帧丢弃（保证已入队的帧不被截断）
```

被丢弃的包数会累计到统计面板。客户端断开时，关闭 socket 并中断发送线程，`join(300ms)` 保证线程不会泄漏。

## 十一、技术关键点 9：真实运行统计

UI 上的「运行统计」不是估算值，而是实际编码输出：

- 编码线程每帧累加 `AtomicInteger / AtomicLong`
- 主线程每秒读取并清零，按时间差计算实际 fps 与 bps
- 客户端数分别统计 RTSP 与 RTP 两路
- 丢包数来自 RTSP 客户端队列

这样可以看到「相机标称 30fps，实际编码只有 27fps」这类真实情况，而不是只显示一个漂亮的目标参数。

## 十二、踩坑实录

1. **预览矩阵按控件铺满**：纹理被压到中间一小块。预览必须按画面比例重算裁剪区域。
2. **FU-A 首片带原始 NAL 头**：首片花屏、后续帧正常，极难定位。
3. **前置镜像与旋转顺序错误**：镜像后再旋转，画面差 180°；必须镜像作用在输出坐标、旋转作用在纹理坐标。
4. **预览与推流双渲染路径**：方向、比例永远对不齐，改一处要验证两处。
5. **横竖屏重建整条相机链**：切换需要数秒。最终只重建编码器与 RTSP/RTP 服务，相机和预览保持不动。
6. **切镜头闪一帧镜像**：异步配置期间旧帧用了新镜像参数。把参数更新延后到新相机真正出帧。
7. **慢客户端阻塞编码线程**：一个客户端卡住，所有观众一起卡。改为每客户端队列。
8. **UDP 广播 15 秒超时**：只收不发的播放器会被清理。需要调大超时或让播放器定期发心跳。

## 十三、性能与质量指标

### 设备要求

- Android 8.0（API 26）及以上
- 支持 Camera2 与 H.264 硬件编码（2016 年后的设备基本满足）
- 建议中端及以上 SoC：1080P30 同时做 GL 纹理复制 + 硬件编码 + 多客户端 RTP 打包，低端机长时间运行会发热降频

### 编码档位与码率

| 档位 | 目标码率（CBR） | 单客户端带宽占用 |
| --- | --- | --- |
| 1080P30 | ≈ 4.35 Mbps | ≈ 0.55 MB/s |
| 720P30 | ≈ 1.94 Mbps | ≈ 0.24 MB/s |
| VGA30 | ≈ 0.8 Mbps（下限） | ≈ 0.10 MB/s |

### 延迟与画质

- 无 B 帧、CBR、编码器实时优先，尽量减少编码排队
- 纯 H.264 + RTP，无转码、无二次封装；理论端到端延迟在数百毫秒量级，实际取决于播放器缓冲
- 关键帧间隔 1 秒，新客户端 1 秒内可出画，丢包后 1 秒内自愈
- 预览与码流同源，构图完全一致；预览只做居中裁剪，不改画面比例

### 已知限制

- 无音频
- UDP 广播是明文、无鉴权，仅限可信局域网
- 只收不发的播放器需要自行处理 15 秒心跳问题
- 推流中不允许切换镜头或分辨率（避免重建链路导致断流）

## 十四、怎么用

启动推流后，应用内会显示两个地址：

### RTSP 拉流

```bash
ffplay -rtsp_transport tcp rtsp://192.168.31.6:8554/live/cam0
# 设置了密码时：
ffplay -rtsp_transport tcp rtsp://admin:123456@192.168.31.6:8554/live/cam0
```

符合标准的 RTSP 播放器（如 VLC）也可接入，建议同样选择 TCP 传输。多客户端可以同时拉同一路流。

### RTP/UDP 广播

接收端需要两个条件：先向手机 9998 端口发一个探测包完成注册；再用 SDP 告诉解码器 `PT 96 = H.264`。

```text
v=0
o=- 0 0 IN IP4 127.0.0.1
s=shiliu
c=IN IP4 127.0.0.1
t=0 0
m=video 6000 RTP/AVP 96
a=rtpmap:96 H264/90000
```

```bash
# 先从一个 UDP 端口向手机 9998 发一个字节完成注册，然后用同一端口收流
ffmpeg -protocol_whitelist file,udp,rtp -i stream.sdp -frames:v 1 out.png
```

由于存在 15 秒离线清理，长时间播放需要周期性发送心跳包。

## 十六、结语

把手机变成摄像头，技术上并不缺轮子：FFmpeg、GStreamer、各类 SDK 都能做。但这个项目真正的价值在于**把每一层都拆开看清楚**：

- 相机能力怎么读，而不是背一张分辨率表
- 方向与镜像怎么算，而不是靠试参数
- RTP 包怎么拼，而不是交给黑盒
- 慢客户端怎么隔离，而不是让编码线程陪葬
- 后台怎么活下来，而不是赌系统不杀

如果你也在做 Android 音视频、Camera2 或自研流媒体协议，希望这些踩坑记录能帮你少走一点弯路。
